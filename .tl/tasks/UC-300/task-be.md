## System steps (main flow)

1. Worker dequeues; UPDATE ProtocolGenerationJob SET status='PROCESSING', started_at=now WHERE id=:id AND status='PENDING'.
2. Load Meeting; load Transcript via meeting_id; read Meeting.language for prompt template selection.
3. Select prompt template per Meeting.language: `EN` -> EN template, `RU` or `AUTO` -> RU template (BRQ-013 / DEC-003). The same value is carried into the RQ-023 section validation. MVP uses a single hard-coded template version (not persisted on job).
4. Submit transcript + selected prompt to ILlmProvider.generate (TECH-011).
5. Parse LLM response into Markdown.
6. Validate four required sections are present: Participants, Discussion Topics, Decisions, Action Items (RQ-023). Missing -> FAILED path.
7. Insert Protocol(meeting_id, markdown_content, version=1, edit_count=0, generated_at=now) (RQ-025).
8. Transition Meeting.status -> PROTOCOL_READY (BRQ-008).
9. Transition ProtocolGenerationJob.status -> DONE, finished_at=now (RQ-021).
10. Publish SSE 'meeting.status' event.
11. ALT failure path (RQ-026 / RC-UC-300): classify the error by **effective status** (`body.code` when an HTTP 200 body carries a numeric `code` != 200, else the HTTP status — full rule embedded under "Runtime contract" below).
    - TRANSIENT (404/408/429/5xx, or a network/transport failure) **and** BullMQ attempts remain -> re-throw WITHOUT any DB write, so BullMQ schedules the next attempt with exponential backoff. Do NOT write FAILED (the BRQ-009 idempotency guard would otherwise make the re-attempt a no-op).
    - PERMANENT (400/401/402/413, any other unlisted 4xx, JSON-parse failure, empty/unparseable completion, missing section) **or** the final exhausted attempt -> mark job FAILED with descriptive error_msg, finished_at=now, attempt_count=attemptsMade+1; Meeting.status -> FAILED; publish SSE; do NOT re-enqueue.

## Runtime contract — RC-UC-300 (embedded; status `approved`, updated 2026-08-13)

**Durable state machine.** `ProtocolGenerationJob.status`: `PENDING → PROCESSING
→ {DONE | FAILED}`, persisted via Prisma. Side FSM on `Meeting.status`:
`TRANSCRIBED → GENERATING_PROTOCOL → {PROTOCOL_READY | FAILED}`.

**Transaction boundaries.** Per BullMQ job. `PENDING→PROCESSING` on pickup;
`DONE` after the Protocol row is created with `markdown_content` from the kie.ai
response; `FAILED` on a non-retriable error.

**Idempotency.** Job key = `meetingId`. The kie.ai call itself is not idempotent
(LLM output varies); the system-level effect is — `Protocol` is created exactly
once via the Prisma uniqueness constraint on `meetingId`.

**Lock.** `RL-UC-300-BULLMQ` — BullMQ job lock, key
`bullmq-job:protocol-gen:<meetingId>`, scope per-meeting, owner `worker`, TTL
30s, auto-renewed. Only one worker generates the protocol for a given meeting at
a time.

**Event.** `RE-UC-300-STATUS` — post-commit SSE `meeting.status`
(`GENERATING_PROTOCOL → PROTOCOL_READY`), payload `{meeting_id, status}`,
published to Redis pub/sub `meeting:<id>`.

**Recovery.** Process crash: the BullMQ lock expires and another worker picks the
job up. The kie.ai call restarts from scratch (no streaming checkpoint) —
re-generation consumes tokens, accepted at MVP scale.

**Cancel race.** Meeting delete during processing: cascade-delete removes the
`ProtocolGenerationJob`; the worker exits cleanly on its next Prisma write.

### Retry semantics (revised 2026-08-13 by DEC-001)

Max 3 attempts, exponential backoff (initial 5s, multiplier 2).

| Class | Effective status | Action |
|-------|-----------------|--------|
| **TRANSIENT** | 404, 408, 429, 5xx; plus network/transport failures (DNS, connection reset, socket timeout) | Re-throw, let BullMQ retry |
| **PERMANENT** | 400, 401, 402, 413, and any other unlisted 4xx; plus local errors (JSON parse failure, empty/unparseable completion, missing required section) | Halt, write `FAILED` at once |

**Effective status.** kie.ai is a gateway that MAY deliver a provider error
*inside* an HTTP 200 response, using the envelope `{code:<int>, msg:<string>}`
(live probe 2026-08-13: an invalid Bearer key returns HTTP 200 with body
`{code:401,msg:'Unauthorized…'}`). Classification MUST therefore run on the
effective status: `effective = body.code` when the HTTP status is 200 AND the
parsed body is an object carrying a numeric `code` other than 200; otherwise
`effective =` the HTTP status. An in-envelope 429/5xx is TRANSIENT; an
in-envelope 400/401/402/413 is PERMANENT. Before DEC-001 an in-envelope error
never reached the classifier at all — it fell through to the empty-completion
branch and was reported as a permanent parse error, which both mis-classified
transient provider errors and hid the real cause from the operator.

**404 is transient** — this reverses the earlier `MODEL_NOT_FOUND` reading. The
model id is sent in the request **body**, never in the URL
(`worker/src/llm/kieai.ts`), so a 404 cannot denote an unknown model; a bad
model id reaches the handler and comes back as an envelope error. Live probes
2026-08-13 show kie.ai answers an unrouted path with a Spring Boot whitelabel
body `{timestamp,status,error,message,path}` — i.e. HTTP 404 means "the gateway
did not route this path", transient by nature (incident 2026-05-26: the
identical request returned HTTP 200 twelve minutes later). A genuinely permanent
404 (a misconfigured base URL, as in commit `1f025b7`) still ends in `FAILED`
once the 3 attempts are exhausted; the cost of the reversal is bounded to 2
extra attempts plus ~15s of backoff.

**FR-001 refinement (unchanged by DEC-001).** The failure handler MUST NOT write
`job.status=FAILED` while BullMQ attempts remain for a TRANSIENT error; it
re-throws so BullMQ schedules the next attempt. The idempotency guard therefore
must NOT treat a non-final state as terminal. `FAILED` (and
`Meeting.status=FAILED`) is written ONLY on a PERMANENT error or on the final
exhausted attempt. `attempt_count` mirrors BullMQ `attemptsMade`.

**Applicability.** Observable only where the enqueued BullMQ job carries
`attempts>1`. The automatic path qualifies (`worker/src/jobs/transcription.ts`
enqueues via `createQueues()`, `attempts=3` + exponential backoff). The UC-004
manual-retry path does NOT: `api/src/queue.ts` builds its Queue without
`defaultJobOptions`, so those jobs get the BullMQ default `attempts=1` and a
transient error still fails them on the first attempt. Known gap, deliberately
out of scope for DEC-001; tracked as **F-004**.
