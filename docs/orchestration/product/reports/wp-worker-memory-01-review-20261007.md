## 3. Answers to the risk questions

**Q1 Isolation.** `scope.ts:47-60` validates both ids as UUIDs, rejects Cypher whose text lacks `$workspaceId`/`$projectId` (`\$workspaceId\b` regex), and refuses caller params named `workspaceId`/`projectId`, so the values always come from the scope. All reads/writes in `reads.ts`, `reviews.ts`, `meeting-update.ts`, `deletions.ts`, `tasks.ts` go through `readScoped`/`writeScoped` and a `ScopedTx` whose `run` applies `scopedParams` (`scope.ts:68-75`). The check **is string-based** and bypassable in principle: a query that mentions `$workspaceId` anywhere (e.g. only in a `COUNT {}` subquery) but omits it from the primary MATCH passes the regex. I audited every Cypher string: all primary MATCH patterns carry both predicates, including `deleteProjectFromGraph` (`WHERE n.workspaceId = … AND n.projectId = …`), the pattern comprehensions in `DECISION_RETURN`/`getMeetingMemoryRefs`, and `materializeTask`. Exceptions: `findTaskEventScope` (`reads.ts:189-210`, by design RQ-055, requires non-empty caller workspaces, test at `scope.test.ts:73-77`); migrations (schema statements, no tenant data); `patchTask`'s `MERGE (p:Participant {id: $id})` (`reviews.ts:135-142`) matches on id alone and then checks ownership — a foreign participant id yields `MemoryNotFoundError`, no data leaks and nothing is modified (tx rolls back), but it is the one MERGE not keyed by tenant. Mutation M1 (removed `workspaceId: $workspaceId` from `listTasksTx`'s MATCH while `TASK_RETURN` still contained the token, so the regex passed): `memory-graph.neo4j.test.ts › a foreign workspaceId sees nothing` failed with `expected [ {…}, {…} ] to deeply equal []` — the integration test, not the regex, is what catches this class of bug; `scope.test.ts` alone would not.

**Q2 Fabrication guard.** `transcript.ts:146-160`: exact = normalised (lower, ё→е, non-alphanumerics → space) whole-word substring with space padding (word boundaries verified by `transcript.test.ts:55-59`); stored text = the LLM's quote (same words up to case/punctuation). Fuzzy (`:162-199`) = share of the quote's tokens present in a **bag** of 1–3 consecutive segments, ≥ 0.85, a negation token in the quote must exist in the bag; stored text = the segments' own text. Word order and extra transcript words (including a transcript-side "не") are ignored. In `gate.ts:180` `sure = confident(r.confidence) && quote.score >= 1`, so a fuzzy match with all words found is "sure". Probe (temporary test, removed): transcript `[#0] "Иванов пока готовит смету." [#1] "А договор заказчику отправил Козлов, не Иванов."`, LLM quote `"Иванов отправил договор заказчику"` → `verifyQuote` returned `{match:"fuzzy", score:1, quote:"А договор заказчику отправил Козлов, не Иванов."}`; `applyGate` with an UPDATE on T-1 (confidence 0.95) produced `[["status","IN_PROGRESS","AUTO"],["assignee","Иван Иванов","AUTO"],["due_date","2026-10-20","AUTO"]]`. Can a mention close/cancel automatically? No: every path to DONE/CANCELLED is PENDING — `CLOSE` → `statusChange(to, true)` (`gate.ts:251-257`), `UPDATE` with closing status → `!CLOSING.includes(to)` false (`:244`), `NEW` with done signal → extra PENDING event (`:214-217`). Change kinds: NEW task → AUTO (even low confidence; declared); MENTIONED → no event; status → IN_PROGRESS/POSTPONED/OPEN → AUTO if sure else PENDING; status → DONE/CANCELLED → PENDING always; `merged_into` (DUPLICATE) → PENDING always; first assignee → AUTO if sure; assignee replacing an existing one → PENDING always; due_date/title/description → AUTO if sure else PENDING; decisions NEW/supersedes → always applied, confidence ignored (no decision review flow exists in the DTOs). Versus D-14 literally: closing, cancelling, merging, reassigning → PENDING ✔; "uncertain" → PENDING ✔ for confidence < 0.7, ✘ for fuzzy-score-1 quotes (Finding 1). Closed tasks are never candidates (`listOpenTasks`), so "reopened" cannot touch a DONE task at all. Mutation M2 (`auto = sure`): `gate.test.ts › CLOSE and status → DONE / CANCELLED are always PENDING` failed.

**Q3 Existing job flow.** Diff stat: 43 files, none under `worker/src/jobs`, `worker/src/llm`, nor `job-processor.ts`, `queues.ts`, `index.ts` (I diffed those paths explicitly: empty). Listener at `index.ts:128-138` is registered on BACKEND-06's `WorkerEventBus`; `emit` (`job-processor.ts:162-172` on main) wraps each listener in `Promise.resolve().catch(onError)` and fires after the protocol job's `completed` event, so a throwing or slow listener cannot delay or fail the protocol job. **Q4 Idempotency and ordering.** ALREADY_APPLIED is keyed by `(:ProjectMemory {workspaceId, projectId, sourceMeetingId: $meetingId})` (`meeting-update.ts:92-94`), checked in the pipeline before any LLM call (`pipeline.ts:100-101`) and again inside the write transaction (`:127-128`). Double delivery: BullMQ `jobId = memory-<meetingId>` dedups adds; two worker processes cannot process the same job concurrently; a replay after completion returns ALREADY_APPLIED without LLM calls (`pipeline.neo4j.test.ts:153-157`). Mutation M7 (short-circuit removed): the re-delivery test failed (with `MemoryConcurrencyError` — the counter check is the second line of defence). Concurrent meetings of one project across two processes: the optimistic check (`:129-140`, compares `taskSeq/decisionSeq/meetingSeq/memoryVersion` read inside the tx with the planned ones) is a read-then-write inside a Neo4j tx and is **not serialised** — two transactions can both pass it; the real backstop is the unique constraints `(projectId, code)` on Task/Decision and `(projectId, version)` on ProjectMemory (`migrations.ts:31-36`): the loser fails with a constraint error → BullMQ retry re-plans with fresh counters (LLM cost ×1). Failure path is error + retry, never silent code reuse. Note `expected.meetingSeq` makes `Meeting.seq` collide only if both commits succeed, which the ProjectMemory version constraint prevents.

## 4. Findings

**Medium — F1. Fuzzy quote with score 1 bypasses the "fuzzy → PENDING" rule.** `worker/src/memory/gate.ts:180` (`const sure = confident(r.confidence) && quote.score >= 1`) together with `worker/src/memory/transcript.ts:166-199` (bag-of-words over a 1–3-segment window, order-insensitive, transcript-side negations ignored). Scenario (reproduced): transcript "…договор заказчику отправил Козлов, не Иванов", LLM quote "Иванов отправил договор заказчику" → accepted as fuzzy/score 1; an UPDATE with confidence ≥ 0.7 then auto-applies first-assignee/due-date/title/description/IN_PROGRESS changes, and the stored quote (the segments' text) contradicts the applied change. Closing/cancel/merge/reassign stay PENDING. Require: `sure` must depend on `quote.match === 'exact'` (not `score >= 1`); add a gate test with `match: 'fuzzy', score: 1` expecting PENDING; optionally make fuzzy matching order-aware or require the window to contain no negation absent from the quote.
